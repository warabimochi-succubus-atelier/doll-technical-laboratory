# どーる技術研究室 投稿アプリ MVP仕様書 v0.2

> v0.1（デスクトップの仕様書）を、現在のサイトの仕組み（制作ログ・どやぁ／ぐぬぬ）に合わせて改訂したもの。
> 変更点のまとめは末尾の「v0.1 からの変更点」を参照。
>
> このアプリは、どーる技術研究室のサイトとこのリポジトリに投稿するためだけの**個人専用ツール**であり、一般向けの配布は想定していない。

## 1. 概要

ドールを撮影・メイクしたあと、iPhone から最小の手順で**制作ログ**をサイトへ公開するための投稿アプリ。

目的はブログ運営ではなく、

> 「撮った・試した・記録した」

を素早く積み上げること。Git 操作や Markdown 編集を意識せず、数タップで投稿できることを最優先とする。

最終目標：

> 作業した証拠を30秒で研究室へ投げ込む装置

## 2. 前提と構成

| 項目 | 内容 |
| --- | --- |
| 形態 | PWA（iPhone のホーム画面に追加して使う Web アプリ） |
| 置き場所 | このリポジトリ内。サイトと一緒にビルドし、`/post/` で配信する |
| 公開先 | GitHub Pages（GitHub Actions でビルド・公開） |
| 公開URL | `https://warabimochi-succubus-atelier.github.io/doll-technical-laboratory/`（アプリは末尾に `post/`） |
| リポジトリ | 公開（Public）にする |
| 利用者 | 自分のみ（1人・1リポジトリ） |
| 認証 | Fine-grained Personal Access Token（§8） |

- `/post/` はナビゲーションに出さず、検索エンジンにも載せない（`noindex`）。
- ページ自体は誰でも開けるが、トークンがなければ何もできない。

### 2.1 アプリより先に済ませること（前提作業）— すべて済み

1. **サイト内のリンクと画像パスを公開URLに合わせる**：サイトは `/doll-technical-laboratory/` の下で公開されるため、
   `astro.config.mjs` に `site` と `base` を設定し、`/logs/` や `/images/…` のような書き方をすべて `base` 付きに直す。
2. **リポジトリを公開（Public）にする**：GitHub の無料プランでは、非公開リポジトリから GitHub Pages を使えないため。
   公開前に、リポジトリに見られて困るものが入っていないか（コミット履歴も含めて）確認する。
3. **GitHub Pages への公開設定**：GitHub Actions のワークフローを追加し、`main` への push でサイトを公開する。

### 2.2 公開リポジトリであることの影響

- コード・制作ログ・写真は、リポジトリを見れば誰でも見られる。
- **一度コミットした写真は、あとでファイルを消しても Git の履歴に残る**（完全に消すには履歴の書き換えが必要）。
- トークンはリポジトリには入れない（端末のブラウザ内にだけ保存する。§8.2）。

## 3. 投稿で作るもの

1回の投稿で、**制作ログ1件と写真（0〜5枚）を、1つのコミットで**リポジトリに追加する。

### 3.1 ファイルの置き場所と名前

名前は「入力した日付」＋「投稿した時刻」（日本時間）で決める。同じ日に複数回投稿しても名前がぶつからない。
（日付を変えて後日まとめて記録した場合も、日付は入力したもの、時刻は投稿した時刻になる。）

| 種類 | 置き場所 | 例 |
| --- | --- | --- |
| 制作ログ | `src/content/logs/` | `src/content/logs/2026-11-19-2130.md` |
| 写真 | `public/images/logs/` | `public/images/logs/2026-11-19-2130-1.jpg` |

- ログのページは `…/doll-technical-laboratory/logs/2026-11-19-2130/` になる。
- 万一同じ名前のファイルがすでにあれば、末尾に `-2` などを付ける。
- 元の写真のファイル名（`IMG_1234.HEIC` など）は使わない。

### 3.2 生成する制作ログ

今のサイトの制作ログと同じ形式で作る。

```markdown
---
date: 2026-11-19
title: "DD桜"
photos:
  - "2026-11-19-2130-1.jpg"
  - "2026-11-19-2130-2.jpg"
photoCaptions:
  - "下塗り"
  - "仕上げ後"
techniques:
  - "ぼかす"
使用材料:
  - "アクリル絵の具"
どやぁ:
  - "頬のぼかしが自然になじんだ"
ぐぬぬ:
  - "左右の濃さがまだ揃わない"
---

メモ（自由記述）
```

- 文字列はすべてダブルクォートで囲み、`"` や `\` はエスケープする（`:` や `#` を含む文でも YAML が壊れないように）。
- 空の項目は見出しだけ残す（サイト側は空欄を許可している）。
- `photos` には `public/images/logs/` に置いた写真の**ファイル名だけ**を書く（公開URLが変わってもログを書き直さずに済むように）。
- `photoCaptions` は写真ごとの短い見出し（`photos` と同じ順、見出しのない写真は `""`）。見出しが1つもないときは項目ごと書かない。
- `techniques` に書くのは技術リストに登録済みの技法だけ（サイトのビルドが通らなくなるのを防ぐ）。

### 3.3 サイト側での写真の表示（サイトに追加する機能）

- 制作ログに `photos`（省略可）の項目を追加する。
- ログ詳細ページ：日付・件名の下に、写真をギャラリーとして並べる。タップで大きく表示する。
- 制作ログ一覧・トップの「最近の制作ログ」：1枚目の写真をサムネイルとして表示する。
- 写真の説明（alt）は「件名 日付 写真N」でサイト側が自動生成する。
- 写真の見出し（`photoCaptions`）があれば、各写真の下と拡大表示の枚数の横に出し、alt の後ろにも付ける。
- 手で書いたログにも、同じ書き方で写真を付けられる。

## 4. 画面

1画面で完結させる。上から順に入力し、最後に「投稿」。

```text
+-----------------------------+
|  ＋ 写真を追加（最大5枚）    |
|  [写真][写真][写真]          |
|  ※ 位置情報などは自動で削除  |
+-----------------------------+
件名          [ DD桜        ▼ ]
実験技術      (細い線)(ぼかす)(グラデーション)…  ← ボタンで選ぶ
使用材料      [               ]
どやぁ        [               ]
ぐぬぬ        [               ]
メモ          [               ]

☐ 写真の背景に、個人情報や見せたくないものが写っていない（新しい写真があるときだけ）
☐ 公開サイトに載ることを理解している

          [ 投稿 ]
```

### 4.1 入力項目

| 項目 | 必須 | 入力方法 |
| --- | --- | --- |
| 写真 | 任意（0〜5枚） | 写真ライブラリから選択。選んだ順に並ぶ。タップで削除。写真ごとに短い見出し（20文字まで・任意）を付けられる |
| 件名 | 必須 | ドール名でも、アイなどパーツの名前でもよい。これまでのログに出てきた件名から選ぶか、新しく直接入力する |
| 実験技術 | 任意 | 技術リストから複数選択（カテゴリ別に表示） |
| 使用材料 | 任意 | 道具も含む。複数行入力。**1行が1項目**になる |
| どやぁ／ぐぬぬ | 任意 | 複数行入力。**1行が1項目**になる |
| メモ | 任意 | 自由記述。ログ本文に入る |
| 日付 | 自動 | 投稿日。必要なら変更できる（後日まとめて記録する場合のため） |

- 使用材料・どやぁ・ぐぬぬとメモが全部空、かつ写真もない場合は投稿できない。
- これまでの件名と技法の選択肢は、サイトのビルド時に投稿画面へ埋め込む（サイトと同時に更新されるため、別ファイルにはしない）。

### 4.2 公開前の確認

- 「投稿」を押したとき、必要なチェックが入っていなければ送信せず、足りないものを表示する。
- 背景のチェックは、新しく選んだ写真があるときだけ、写真のプレビューのすぐ下に出す。
- 写真の縮小中は「投稿」を押せない（縮小が終わる前に送ると写真が入らないため）。**一度コミットした写真は、あとで消しても Git の履歴に残る**ため、ここが最後の確認になる。

## 5. 画像の処理

すべて端末の中（ブラウザ内）で行い、加工後の画像だけを送る。

| 項目 | 設定 |
| --- | --- |
| サイズ | 長辺 1600px（それより小さい写真は拡大しない） |
| 形式 | JPEG 品質 80% |
| 向き | 写真の回転情報を反映してから描き直す |
| メタデータ | 描き直すことで EXIF（位置情報・撮影機種など）はすべて消える |

- iPhone の HEIC 写真は、Safari が選択時に JPEG へ変換したものを使う。
- 1枚あたりおよそ 300〜600KB を想定。

## 6. 送信の流れ

### 6.1 利用者の操作

```text
写真を選ぶ → 件名・技法・研究成果を入力 → チェック → 投稿
```

### 6.2 アプリの処理

```text
画像を縮小・再エンコード
↓
制作ログ（Markdown）を生成
↓
GitHub API（Git Data API）で 1コミットにまとめて追加
  1. main の最新コミットを取得
  2. 画像とログを blob として作成
  3. それらを含む tree を作成
  4. commit を作成
  5. main をそのコミットに進める
↓
GitHub Actions がサイトをビルド・公開（1〜2分）
```

- 1ファイルずつ送る Contents API は使わない（ファイルごとにコミットが分かれ、途中で失敗すると半端な状態が残るため）。
- 手順5で「main が先に進んでいた」と言われた場合、新規投稿（新しいファイルを足すだけ）は1から自動でやり直す（1回まで。作った blob はそのまま使う）。編集・削除・技術リストの変更は、やり直すと先に入った変更を古い内容で上書きするおそれがあるため、自動ではやり直さずエラーにする（技術リストはそのとき最新の内容を読み直す）。
- コミットメッセージ：`Add log: 2026-11-19 DD桜`

## 7. メッセージ

| 状況 | 表示 |
| --- | --- |
| 送信成功 | ✅ 送信しました。数分でサイトに反映されます（ログのURLを表示） |
| 送信失敗 | ❌ 送信できませんでした（理由を1行で表示） |
| トークン切れ・権限不足 | トークンの有効期限が切れているか、権限が足りません。設定から入れ直してください |
| 通信できない | 通信できませんでした。電波のよい場所でもう一度お試しください |

- 失敗しても入力内容と写真は消さず、そのまま「もう一度送信」できるようにする。
- 成功したら入力欄を空にする。

## 8. GitHub の設定

初回起動時に1回だけ入力する。

| 項目 | 例 |
| --- | --- |
| リポジトリ | `warabimochi-succubus-atelier/doll-technical-laboratory` |
| トークン | Fine-grained Personal Access Token |

### 8.1 トークンの作り方（推奨設定）

- Repository access：**このリポジトリだけ**
- Permissions：**Contents を Read and write**（それ以外は付けない）
- 有効期限：あり（例：90日。切れたら作り直して入れ直す）

漏れても「このリポジトリへの書き込み」以上のことはできない範囲に絞る。

### 8.2 保存先

- トークンは端末のブラウザ内（IndexedDB）に保存する。iPhone の Keychain は PWA からは使えない。
- 保存領域は `warabimochi-succubus-atelier.github.io` 単位で共有される。同じアカウントで GitHub Pages のサイトを増やす場合は、そのサイトに他人のコードを入れないこと。
- サーバーには送らない（GitHub API 以外へは一切送信しない）。
- 設定画面に「トークンを削除」ボタンを置く。

### 8.3 OAuth / GitHub App を使わない理由

GitHub OAuth も GitHub App も、ログインの途中に秘密の鍵を使う処理があり、そのためのサーバーが別に必要になる。GitHub Pages に置くだけの PWA とは相性が悪く、利用者も1人なので、MVP ではトークン方式とする。

## 9. MVP で実装しないもの

- 下書き保存（送信失敗時に入力を残すのは対象。§7）
- 公開予約
- 検索
- AI 要約
- コメント
- SNS 共有
- 複数リポジトリ・複数ユーザー対応
- オフライン時の送信待ち（キュー）
- Service Worker によるオフライン起動（MVP はホーム画面への追加と全画面表示のみ）

## 9.1 追加済み：投稿済みログの編集・削除

- 「過去の投稿」タブに、`src/content/logs/` のログを GitHub から直接読んで新しい順に表示する（10件ずつ。サイト未反映の投稿も出る）。
- 編集：投稿画面に読み込み、内容を書き換えて「更新」。写真は外す・足すことができる（合計5枚まで）。
  - ファイル名（URL）は変えない。新しい写真は `ログ名-e編集日時-番号.jpg`（例：`2026-11-19-2130-e202611211830-1.jpg`）にする。前に外した写真と同じ名前にすると、Pages やブラウザに残った古い写真がしばらく表示されるため。
  - 外した写真はリポジトリから削除する。ログの更新と写真の追加・削除は 1 コミット（`Edit log: …`）。
- 削除：確認のうえ、ログと付いている写真をまとめて 1 コミットで削除する（`Delete log: …`）。Git の履歴には残る。
- 手書きのログ（引用符なしの YAML、行末コメントあり、`[項目, 項目]` の形のリスト、`-` を字下げしないリスト）も読み込める。
- `|` や `>` で複数行にした値など、アプリで読めない書き方があるログは、読み違えたまま上書き保存して中身が消えないよう、読み込まずにエラーにする（どの行かを表示する）。技法の改名・削除で制作ログを調べるときも同じ。
- 写真は 1MB を超えていても読み込める（contents API が中身を返さないときは blob API で取り直す）。

## 9.2 追加済み：技術リストの編集

- 「技術リスト」タブに、`src/content/techniques/` の技法を GitHub から直接読んで、研究分野・カテゴリ別に表示する（技法のないカテゴリも表示）。
- 追加：技法名・カテゴリ・メモを入力。カテゴリの最後に並ぶ（`Add technique: …`）。
- 編集：名前・カテゴリ・メモを変更（`Edit technique: …`）。カテゴリを移すと移動先の最後に並ぶ。
- 名前の変更：技法名はファイル名（＝技法 ID・URL）でもあるため、ファイル名を変え、その技法を使っている制作ログもまとめて書き換える（1 コミット、`Rename technique: 旧 → 新`）。
- 並べ替え：↑↓ でカテゴリ内の順番を入れ替え、そのカテゴリの order を 1, 2, 3… に振り直す（`Reorder techniques: …`）。
- 削除：制作ログで使われている技法は、サイトのビルドが止まるため削除できない（使っているログを表示する）。
- 技法名には `\ / : * ? " < > | # %`・制御文字・先頭と末尾の `.`・Windows で使えない名前（`CON` `NUL` `COM1` など）は使えない（ファイル名・URL になり、手元の Windows でも扱うため）。同じ名前（大文字小文字違いを含む）は登録できない。
- 技術リストを変えると、投稿画面の技法ボタンもその場で更新する。

## 9.3 追加済み：カテゴリ・研究分野の編集

- カテゴリと研究分野は `src/data/categories.json`（`{ "fields": [{ "name", "categories": [] }] }`）に置き、サイト（技術リスト・研究室紹介・ビルド時のチェック）とアプリの両方がここを読む。
- 「技術リスト」タブの「カテゴリ・研究分野を編集」で切り替える。
- 研究分野：追加・名前の変更・並べ替え・削除（カテゴリが入っている研究分野は削除できない）。
- カテゴリ：追加・名前の変更・別の研究分野への移動・並べ替え・削除（技法が入っているカテゴリは削除できない）。
  - 名前を変えると、そのカテゴリの技法ファイルの `category` もまとめて書き換える（1 コミット、`Rename category: 旧 → 新`）。
  - 別の研究分野へ移すと、移動先の最後に並ぶ。
- 同じ名前のカテゴリ・研究分野は作れない。名前は30文字以内で、`\` と `"` は使えない。カテゴリを1つも無くすことはできない。
